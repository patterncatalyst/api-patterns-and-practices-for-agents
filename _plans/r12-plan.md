# r12 Implementation Plan: ch37 (Running on Kubernetes with Strimzi) + ch38 (Final project: the focused multi-domain data mesh)

Status: APPROVED with decisions (owner 2026-11-20). The book's final two chapters. Biggest shift in the book: `docker compose` -> minikube cluster. All house gates apply. OpenShift/CRC is OUT (Appendix B, r14).

**LOCKED DECISIONS (owner 2026-11-20):**
1. **SPLIT: r12a = ch37 + `examples/_k8s/` platform + one reference service (verified headless); r12b = ch38 the 3-product mesh.** Build r12a first, ship it as a clean checkpoint, then r12b.
2. **3 data products** (ch38): orders (ch13/07/08), shipping (ch14/17), payments (ch15 gRPC); governance as a cross-cutting plane (Apicurio + Keycloak + ch21/34 audit). No 4th (inventory) product.

6. New host/operator pins (minikube, Kubernetes `--kubernetes-version`, kubectl, helm, Istio, istioctl, Kiali) surveyed to latest stable and recorded in versions.md at G0 with reasons; this approval authorizes them.

## Approach

The shift to a minikube cluster is the real deliverable; the two chapters ride on it.

- **ch37 = the self-serve platform.** A setup/non-pattern chapter that stands up ONE minikube profile (docker driver, containerd), installs operators/platform with Helm (Strimzi, CloudNativePG, LGTM + OTel) plus the book's identity/registry/model components (Keycloak, Apicurio, Ollama), loads UBI10 images with `minikube image load` (no registry), and deploys ONE already-built service to prove the substrate. Shared platform assets live in `examples/_k8s/`.
- **ch38 = the finale.** A non-pattern project chapter that deploys 3 agent-facing DATA PRODUCTS (reusing existing chapter services, adapted, never re-forked) onto the ch37 cluster, maps them onto Dehghani's four principles, and verifies one agent-driven scenario end to end across the products, headless, asserting captured side effects. It ties the catalog together; it introduces no new pattern.
- **Verification contract re-defined for a cluster** (the r12 analogue of the compose fresh-run): profile create (NodePorts via `minikube start --ports=127.0.0.1:<np>:<np>`) -> helm install operators gated on readiness -> apply Kafka/Postgres CRs + `kubectl wait` -> `minikube image load` -> `kubectl apply -k` -> `kubectl rollout status` -> assert via NodePort `curl`, `kubectl exec` psql, and `kcat` against a Kafka NodePort -> teardown. Run locally in the cluster lane, logged in `_plans/verification-log.md`. `kubectl exec`/`kubectl logs` are allowed (not forwarding); `kubectl proxy`, `port-forward`, `minikube tunnel` are banned and already caught by `validate.py`'s `FORWARDING` regex.
- **RECOMMEND SPLIT into r12a (ch37 + platform) and r12b (ch38 mesh).** See Open questions. Waves are sequenced so ch37 is a clean checkpoint regardless.

Rejected alternatives: keep port-forward/tunnel (banned); `minikube docker-env` to skip image load (profile uses containerd, needs `minikube image load`); make ch37/38 pattern chapters (neither states a new pattern, both use the setup spine); build the mesh from scratch / copy the datamesh sibling (violates no-sprawl + reuse-by-reference); adopt Istio/KEDA/Kiali/OpenMetadata now (laptop budget; not needed to show the principles); rely on the `quarkus-kubernetes` extension to generate manifests (the book hand-authors kustomize so the reader sees exactly what applies).

  2. **Shipping data product** — reuse ch14 (shipping tools) + ch17 (reacts to `apa.payments.processed`, books FASTLINE/AIRCO). Ports: Kafka event (async) + MCP track/ETA tool + AsyncAPI.
  3. **Payments data product** — reuse ch15 (payment as gRPC behind an MCP facade). Ports: gRPC + MCP facade.
  - Governance is a cross-cutting PLANE across all three (not a 4th product): Apicurio BACKWARD gate (ch32), Keycloak OIDC scopes on MCP tools (ch16), replayable audit log (ch21, ch34).
  - Optional 4th (owner): Inventory data product (reserve-stock from ch20) if budget allows. Entities/events/topics only from `_plans/domain-model.md`.
- **Each product made agent-facing:** (a) an MCP tool surface (output port for agents), (b) a committed contract (reuse existing `contracts/*`), (c) observability to LGTM over OTLP, (d) a governance hook (Apicurio rule + Keycloak scope). Each independently deployable: own Deployment/Service, own Postgres schema in the one CNPG cluster, own Kafka topics on the one Strimzi cluster.
- **Dehghani's four principles -> concrete build:** domain ownership (one product per domain, owns schema/topics/Deployment, no shared mutable store); data as a product (discoverable, self-describing, observable ports: MCP + contract + llms.txt + LGTM); self-serve platform (the ch37 cluster + shared kustomize base + ConfigMap); federated computational governance (Apicurio BACKWARD on every schema, Keycloak scopes on every write tool, schema enforcement on ingest, the append-only replayable audit log both directions).
- **Deploy:** `kubectl apply -k examples/_k8s/overlays/minikube` adds the 3 product Deployments/Services onto the running ch37 cluster; images via `load-images.sh`. One cluster, one profile.
- **Observable effect verify.sh asserts (agent-driven, end to end):** drive the orders product's MCP tool over its NodePort to place/advance an order -> payments takes payment (gRPC) + publishes `apa.payments.processed` -> shipping wakes on the Strimzi topic + books a carrier + writes a shipment row -> the audit plane records both the inbound tool call and the outbound model call. Assert captured side effects only: CNPG rows via `kubectl exec psql` across orders/payments/shipping schemas, Kafka records via `kcat`, the audit replay reproduces the live projection, Tempo/Mimir/Loki signals via the Grafana NodePort. Never model prose.
- **Biting negative witness (cluster mesh-hop cut):** scale the shipping product to 0 (or a NetworkPolicy / drop-event filter) so `apa.payments.processed` is never consumed; the order is recorded and paid but no shipment row and no notification appear, isolating the break to one hop (ch18 drop-event witness on the cluster). Alt: register a BACKWARD-incompatible schema and assert the governance gate rejects it. Restore and reverify green.
- **New contracts:** reuse existing `contracts/*` (07 OpenAPI, 13/14/15 MCP, 15 .proto, 17 AsyncAPI, 21 audit). Add `contracts/38-data-mesh-catalog.md` (or `.json`): a per-product descriptor (domain owner, output ports, contract location, SLO/governance rule, NodePort), standing in for the discovery catalog the sibling documents but does not build (OpenMetadata deferred).

- **Image load / ErrImageNeverPull / ImagePullBackOff:** bare names + `imagePullPolicy: Never`/`IfNotPresent` fail if the exact name:tag was not loaded or after a profile recreate. DETECT rollout-status timeout -> `describe pod`; load-images.sh builds from the examples/ reactor root.
- **Operator readiness ordering:** a CR before its operator/CRD is Ready hangs. MITIGATE tiered bootstrap with `kubectl wait --for=condition` gates; `kafka.strimzi.io/v1` only.
- **Ollama on K8s:** 4g, model pull, PVC for `/root/.ollama`. DETECT readiness probe on `ollama list`; pre-pull the pinned qwen3 model before app pods. MITIGATE MODEL=off for `mvn -B verify` so CI never needs Ollama.
- **Flaky waits/timeouts:** explicit `kubectl wait --for=condition=Ready --timeout=...` with component-specific generous timeouts; NodePort curl retries; a hang surfaces as a failed wait, not a false pass.
- **K8s "newer than supported" warnings (CNPG/KEDA matrices lag):** warnings not failures (sibling verified live); record the hold in versions.md.
- **validate.py compose-vs-cluster gap:** without Wave A, check_examples fails `37-`/`38-`; the new `--self-test` cases must plant+catch a non-fresh cluster verify.sh.
- **Shared-file contention:** strict wave serialization, no worktrees, checkpoint-commit per chapter.

## r12b design decisions (ch38, locked by orchestrator 2026-11-20 after app recon + owner correction)

Reconnaissance of the four reused apps (13 orders, 14 shipping-read, 15 payments facade+gRPC backend, 17 shipping-writer) surfaced three facts that drive the design:
- **Shared-DB Flyway collision:** apps 13 and 14 both set `default-schema=orders` and both migrate the `orders` schema against the one `apa` database; their `orders.flyway_schema_history` would collide (see [[feedback_multi_app_shared_db_flyway]]).
- **No app produces `apa.payments.processed`:** app 15's payment-service writes `payments.payments` but never publishes to Kafka; app 17 consumes `apa.payments.processed`. The producer must be stood in for.
- **None of the four is OIDC-gated** (no `quarkus-oidc`); the Keycloak-scope governance facet cannot be shown as a live 403 from these reused apps.

Decisions:
1. **Per-product database** in the one CNPG cluster (`orders`, `payments`, `shipping`), created idempotently via `kubectl exec psql` in ch38's verify.sh before the apps deploy. Each app's overlay overrides `QUARKUS_DATASOURCE_JDBC_URL` to its product's own database. This resolves the Flyway collision AND is the concrete named artifact for Dehghani principle 1 (domain ownership, no shared mutable store). ORDERS=`orders` (app 13), PAYMENTS=`payments` (app 15 payment-service; facade has no DB), SHIPPING=`shipping` (apps 14+17, distinct schemas/history, no collision).
2. **5 deployments / 3 products:** ORDERS=13; PAYMENTS=15 mcp-facade + payment-service (gRPC 9000, internal); SHIPPING=17 event-writer + 14 track/eta read-port.
3. **App host access = NodePorts, NOT ClusterIP-only.** Owner correction 2026-11-20: there is no "apps must be ClusterIP" house rule; CLAUDE.md bans only *forwarding* and endorses NodePorts. The r12a `base/app-template.yaml`/overlay comments that said "never a NodePort" were a self-imposed r12a convention and are corrected in r12b. The three host-facing product surfaces (orders `/mcp`, payments facade `/mcp`, shipping-read `/mcp/shipping`) get NodePort Services with pinned nodePorts, added to `lib/endpoints.sh` (orders host 8088/np 30388, payments 8089/30389, shipping-track 8090/30390; adjust at bring-up if a host port is busy). verify.sh drives them with `curl` over `127.0.0.1:<hostPort>`, reusing the MCP-over-HTTP call sequences from the reused apps' own compose verify.sh. App 17 stays ClusterIP (no host-facing tool; driven by Kafka event, asserted via DB). payment-service (gRPC backend) stays internal.
4. **The payments→event hop is stood in for by `kcat`** producing `apa.payments.processed` to the Kafka NodePort (exactly as ch37's verify.sh does), documented as payments' async output port in the catalog. No app is modified to publish.
5. **Governance plane:** Apicurio BACKWARD gate = the **live biting** governance witness (reuse ch32's mechanism against the cluster Apicurio NodePort). Keycloak realm scopes + the replayable-audit obligation = named governance rules per product in `contracts/38-data-mesh-catalog`, documented honestly (not a live 403, since the reused apps are not OIDC-gated).
6. **Biting negative witness = mesh-hop cut:** scale shipping-17 to 0, produce `apa.payments.processed` for a second order, assert NO `shipping.shipment_prep` row (paid but unshipped), restore to 1, assert the missed event is read (ch37/ch18 translated; assert the DB row, never a metric absence).
7. **load-images.sh** must be extended for app 15's two sub-directory Containerfiles (no top-level Containerfile): build `localhost/apa/15-reshape-grpc-behind-facade-mcp-facade:1.0.0` and `...-payment-service:1.0.0` with the context each Containerfile expects.

Four Dehghani principles → concrete named artifacts: domain ownership = per-product databases + per-product Deployment/schema/topics; data as a product = each product's output ports (MCP + contract + async + observability) in `contracts/38-data-mesh-catalog`; self-serve platform = the ch37 cluster + shared `base/config.yaml` ConfigMap + the ch38 aggregate kustomize overlay; federated computational governance = the live Apicurio BACKWARD gate + the per-product Keycloak scope + audit rules named in the catalog.
